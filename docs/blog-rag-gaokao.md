# 我用 RAG 技术做了一个高考志愿 AI 顾问，它是怎么工作的？

> **系列第 1 篇 | 从零搭建领域 RAG 系统的完整技术复盘**
>
> 本文约 4500 字，阅读时间 12 分钟。如果你对 RAG、提示词工程、或 AI+教育 感兴趣，这篇文章应该能给你一些启发。

## 为什么做这个东西？

高考志愿填报，可能是中国家庭面临的最重要的决策之一。

但现实是：优质志愿咨询资源严重不均衡。好的志愿规划师动辄收费几千甚至上万，而且集中在一线城市。大部分三四线城市和农村家庭，要么花冤枉钱找不靠谱的机构，要么自己在网上到处搜碎片信息，最后凭"感觉"填。

我想试试能不能用 AI 技术做一个**免费的、有专业水准的志愿顾问**。

说起来简单，做起来问题一大堆。纯 LLM 回答高考志愿问题，最大的问题就是**它会编**。编学校、编分数、编录取线——这些信息如果错了，可能真的会影响一个孩子的一生。

所以我的核心思路是：**让 AI 说话有依据，每一个建议都能追溯到真实数据。**

这就是为什么我选择了 RAG（Retrieval-Augmented Generation，检索增强生成）作为技术路线。整个系统基于 3000+ 院校、68000+ 分数线数据、838 行知识库和 105 条专家语录，目前已经开源。

---

## 技术选型：为什么选 RAG？

在项目初期，我认真评估了三种技术路线：

### 方案 A：纯 Prompt Engineering

直接在 system prompt 里塞入所有知识，让 LLM 回答。

**优点**：实现简单，零依赖。

**致命问题**：
- 知识库有 838 行、17 个模块，塞进 prompt 后 token 开销巨大
- 无法做到"按需检索"——问专业选择却加载了考研知识，白白浪费 token
- 随着知识量增长，上下文窗口很快不够用

### 方案 B：微调（Fine-tuning）

用高考志愿领域的问答数据微调一个模型。

**优点**：回答风格稳定。

**致命问题**：
- 数据时效性差——分数线每年变化，微调模型无法实时更新
- 高考政策每年调整，重新微调成本高
- 仍然无法根治幻觉问题，模型"记住"的只是概率分布，不是精确数据

### 方案 C：RAG + 高质量提示词 + 质量控制

用 RAG 做知识检索，用精调的提示词控制表达风格，用多层质量控制模块防止错误输出。

```
┌─────────────────────────────────────────┐
│          "三板斧"架构                    │
│                                         │
│  1. RAG 检索     → 知识有据可查          │
│  2. 提示词工程    → 表达有风格有底线       │
│  3. 质量控制      → 输出有审查有兜底       │
│                                         │
└─────────────────────────────────────────┘
```

最终我选了方案 C。原因很实际：

- **可控**：知识来源透明，出错能定位到具体哪个环节
- **可更新**：分数线数据每年更新，只需刷新数据库，不用重新训练
- **可解释**：用户问"你为什么推荐这个学校"，系统能给出依据
- **成本低**：不需要 GPU 微调，一个 OpenAI 兼容 API 就能跑

## 系统架构：从用户输入到推荐输出

先放一张完整的系统流程图，然后逐层拆解：

```
用户输入: "山东考生，580分，想学计算机"
            │
            ▼
    ┌──────────────────┐
    │   Prompt 注入检测  │  ← 安全边界
    └────────┬─────────┘
             │
    ┌────────▼─────────┐
    │   意图识别 (17词)  │  ← 判断是否是志愿咨询
    └────────┬─────────┘
             │
    ┌────────▼─────────┐
    │  槽位提取 (7 slots)│  ← 省份/分数/选科/兴趣/目标/地域/家庭
    └────────┬─────────┘
             │
    ┌────────▼──────────────────────────────────┐
    │              RAG 知识检索                    │
    │  ┌────────────┐  ┌────────────┐            │
    │  │ 向量搜索 0.6 │ + │ 关键词 0.4  │  混合评分  │
    │  └────────────┘  └────────────┘            │
    │         ↓                                  │
    │  6 知识组 × 17 模块 + 105 条专家语录        │
    └────────┬──────────────────────────────────┘
             │
    ┌────────▼─────────┐
    │  多源数据管线       │
    │  T1 SQLite (90分)  │  ← 本地 3000+ 院校数据
    │  T2 百度API (70分) │  ← 实时外部数据
    │  T3 搜索   (40分)  │  ← 兜底
    └────────┬─────────┘
             │
    ┌────────▼─────────┐
    │  7 个质量控制模块   │  ← 情绪/交叉验证/AI风险/反模式...
    └────────┬─────────┘
             │
    ┌────────▼─────────┐
    │  LLM 推理生成      │  ← OpenAI 兼容 API
    └────────┬─────────┘
             │
    ┌────────▼─────────┐
    │  后处理 + 免责声明  │
    └────────┬─────────┘
             │
            输出: "你这个分在山东，计算机类能冲 XX 大学..."
```

下面重点说几个关键设计。

### 槽位采集系统

每次对话，系统会从用户消息中提取 7 个槽位（slots）：

```python
SLOTS = {
    "province":     "省份",      # 山东
    "score_rank":   "分数/位次",  # 580分 / 28000名
    "subject":      "选科",       # 物化生
    "interest":     "专业兴趣",   # 想学计算机
    "region":       "地域偏好",   # 想去北京
    "family":       "家庭资源",   # 父母是公务员
    "goal":         "核心诉求",   # 想考公
}
```

槽位提取用的是**级联正则管道**，不是 LLM，因为：

1. 速度极快（毫秒级），不消耗 API 额度
2. 确定性强，同样的输入保证同样的输出
3. 可以处理中文口语的各种变体

几个有意思的处理细节：

**省份检测**不只识别"我是山东人"这种标准说法，还做了方言推断——

```python
# 方言 → 省份推断
"俺"  → 山东 or 河南
"阿拉" → 上海
"额"  → 陕西 or 甘肃
"不晓得" → 四川 or 湖南
```

**分数识别**支持 5 种输入方式：

| 输入方式 | 示例 | 处理方法 |
|---------|------|---------|
| 阿拉伯数字 | 580分 | 正则直接提取 |
| 中文数字 | 五百八十分 | 中文数字转换 |
| 口语化表达 | 五百八、六百出头 | 自然语言解析 |
| 线差表达 | 差一本线10分 | 换算为绝对分数 |
| 位次表达 | 28000位次、2.8万位次 | 单位统一转换 |

**选科组合**支持 3+1+2 模式下的 12 种组合 + 3+3 模式下的 20 种组合，还包括排列变体（"政史地" = "史政地"）和自然语言解析（"选了物理化学地理"）。

### RAG 检索引擎

知识库被分成 6 个知识组（Group），每组有对应的关键词触发器：

```
G1 核心方法  → "志愿""冲稳保""位次""投档"
G2 专业学校  → "专业""学校""985""学科评估"
G3 就业前途  → "考公""考研""AI""铁饭碗"
G4 生活规划  → "城市""地域""专科""新高考"
G5 数据格式  → "数据""可信度""格式"
G6 速查参考  → "速查""一览""对照""快速"
```

检索采用**向量 + 关键词混合评分**：

```python
hybrid_score = 0.6 * cosine_similarity + 0.4 * keyword_match_score
```

关键词评分是非线性的：

```python
# 0 命中 → 0.0 分
# 1 命中 → 0.4 分
# 2 命中 → 0.7 分
# 3+ 命中 → 1.0 分
```

这样设计是因为：纯向量搜索可能漏掉关键的专业术语（比如"强基计划"），而纯关键词搜索又缺乏语义理解。混合两者，取长补短。

最终检索流程：

1. 将用户消息编码为向量
2. 对 6 个知识组分别计算混合得分
3. 选取 Top 2 知识组（阈值 0.3）
4. 从选中组里按余弦相似度选 Top chunks
5. 同时检索专家语录（向量匹配 + 专业名精确匹配加分 0.3）

支持三种 embedding 后端：OpenAI API、Ollama 本地模型（bge-m3）、以及纯关键词模式（零成本降级）。

### 多源数据管线

高考数据查询采用三级降级策略：

```python
# T1：本地 SQLite（置信度 90）
# 包含 3003 所院校、193 个专业、7000+ 条录取分数

# T2：百度高考 API（置信度 70）
# 实时抓取，按省份自动选择 curriculum 类型

# T3：搜索引擎（置信度 40）
# 兜底方案，从公开网页提取结构化数据
```

每次数据查询都会标注来源等级，最终展示给用户时会标注数据来源和置信度。

一个典型例子——用户问"北京大学在广东的录取线"：

1. 先查本地 SQLite（T1），找到了 → 返回，置信度 90
2. 本地没有 → 调百度高考 API（T2），找到了 → 返回，置信度 70
3. API 也超时 → 触发搜索引擎兜底（T3），返回，置信度 40
4. 如果都没有 → 明确告知用户"该数据暂缺"，**绝不编造**

## 最难的 3 个问题

### 难题 1：让 AI 说人话，不说套话

这是整个项目花时间最多的部分。

直接用 GPT-4 或 DeepSeek 做志愿咨询，你会发现它有一种根深蒂固的"AI 腔"：

> ~~"综合评估您的情况，580分的成绩在山东省具有一定的竞争力。建议您可以考虑以下几个方向：首先，计算机科学与技术专业具有良好的发展前景，但具体选择还需要结合您的个人兴趣和职业规划来综合考虑。希望以上建议对您有所帮助。"~~

这段话有什么问题？

- 开头没有判断，先"综合评估"一圈废话
- "具有良好的发展前景"——套话中的套话
- "具体选择还需要结合您的个人兴趣"——说了等于没说
- "希望以上建议对您有所帮助"——客服标准结尾

**这不是顾问，这是客服。**

我需要的风格是这样的：

> "580 分山东考生？计算机方向？我直接说——你这分冲不了 985 的计算机，但山东科技大学、青岛大学的计算机类，稳得住。家里要是有人在 IT 行业，这两个学校的性价比比你硬冲一个末流 211 强太多了。"

怎么实现的？核心是三个机制：

**机制一：禁词表**

```markdown
### 禁词列表（这些词绝不能出现）

- 或许 / 可能 / 这取决于
- 综合评估 / 建议您 / 具有良好的发展前景
- 在某种程度上 / 一般来说 / 一定程度上
- 仅供参考 / 希望对您有帮助
```

一共 30+ 个禁词/禁句，出现在输出中就判定为不合格。

**机制二：8 种开场白模板（强制轮换）**

```markdown
1. 反问开场："你想学XX？你知道XX专业毕业都去干啥吗？"
2. 直接判断："你这情况我直接说——XX分XX省，你的最优解是XXX。"
3. 先夸再怼："不错不错，580分挺有竞争力。但是你这个想法我得先给你泼盆冷水。"
4. 叹气开场："唉，你这个情况我见的太多了。"
5. 拍桌子开场："成了！580分湖北，你这条件可以横着走。"
6. 冷笑开场："你又看到哪个营销号了？我跟你说真相……"
7. 设问开场："你知道XX专业出来最怕啥吗？"
8. 类比开场："你这种就跟我当年一样，专科毕业，从零开始爬。"
```

强制轮换，不能连续两次用同一种风格。

**机制三：节奏公式**

每段回答遵循 **铺垫 → 反转 → 金句** 的节奏：

> **铺垫**："你这个分想学金融？"
> **反转**："我跟你说句不好听的，普通家庭学金融出来就是给富二代打工的。除非你能考到 985 的金融实验班，否则就是陪跑。"
> **金句**："家里没矿，别碰金融。"

金句要求：不超过 30 字，能让人截图发朋友圈，有反常识洞察。

### 难题 2：数据质量控制

AI 给错数据，在高考志愿场景下后果很严重。所以我搭了一套 7 层质量控制管线：

```
用户输入
    │
    ▼
[1] 情绪检测 ──── 检测危机情绪，触发特殊回复策略
    │              (14个高危词 +30分, 19个中危词 +15分, 10个低危词 +5分)
    │
    ▼
[2] 槽位验证 ──── 至少 4/7 个槽位填充后才给建议
    │
    ▼
[3] 交叉验证 ──── 多源数据比对
    │              (分差容差 5 分，位次容差 10%)
    │
    ▼
[4] AI 时代风险评估 ── 专业被 AI 替代的风险评级
    │                  (红区/黄区/绿区)
    │
    ▼
[5] 反模式检测 ──── 8 条规则检测 AI 常见错误
    │              (模糊判断、未问家庭就推热爱、用顶尖案例推专业...)
    │
    ▼
[6] 自动评分 ──── 8 维度打分 (0-100)
    │              (明确判断/金句/禁词/口语化/数据引用/无编造/长度/无MD)
    │
    ▼
[7] 免责声明 ──── 自动注入数据来源标注和风险提示
    │
    ▼
最终输出 (评分 < 60 分则重写)
```

几个重点模块的实现细节：

**情绪检测**是零成本的纯关键词匹配，不需要 LLM 调用：

```python
# 三级关键词权重表
_KEYWORD_TIERS = [
    # 高危 (+30)
    (["崩溃", "想死", "不想活", "绝望", "想自杀", ...], 30),
    # 中危 (+15)
    (["焦虑", "考砸了", "压力大", "完犊子了", ...], 15),
    # 低危 (+5)
    (["紧张", "纠结", "美滋滋", ...], 5),
]

# 分数阈值
# >= 70 → 危机模式：先安抚，附心理热线，弱化志愿建议
# >= 30 → 共情优先：先共情再分析
# <  30 → 标准模式：正常咨询流程
```

当检测到危机情绪时，系统会自动在回复前注入心理援助热线，并切换到"共情优先"策略，暂时弱化分数和志愿相关内容。

**反模式检测器**是 253 行的规则引擎，核心 8 条规则：

| # | 反模式 | 严重度 | 示例 |
|---|--------|--------|------|
| 1 | 模糊判断 | error | "这取决于个人情况" |
| 2 | 未问家庭就推热爱 | error | "追随你的热爱" |
| 3 | 用顶尖案例推专业 | error | "某大厂年薪百万" |
| 4 | 学院派引经据典 | warn | "波普尔说..." |
| 5 | 空谈 AI 时代 | error | "AI 时代需要跨学科人才" |
| 6 | 过度模糊用词 | warn | 一句话 3 个"可能" |
| 7 | 结论前铺垫太长 | warn | 4 段了还没给判断 |
| 8 | 学术腔开头 | warn | "综上所述" |

触发 error 级别规则的回复会被标记为不合格。

**自动评分系统**从 8 个维度给每条回复打分：

```python
# 满分 100 分
_score_criteria = {
    "第一句判断":    15,  # 开头必须给结论
    "金句(<=30字)":  15,  # 收尾要有记忆点
    "无禁词":        15,  # 禁词表合规
    "口语化>=70%":   15,  # 短句+动词+语气词占比
    "数据引用":      10,  # 标注来源年份
    "无编造数据":    10,  # 数据有出处
    "长度50-800字":  10,  # 不能太短也不能太长
    "无MD格式":      10,  # 不能输出 Markdown 标记
}
# 评分 < 60 → 标记需要重写
```

这套机制的效果是：AI 的输出经过 7 层过滤，每一层都有明确的检测规则和处理策略。不完美，但比裸跑 LLM 靠谱得多。

### 难题 3：30 省差异化处理

中国高考是全世界最复杂的考试制度之一。光选科模式就有三种：

```
┌─────────────────────────────────────────────────────┐
│                  高考选科模式                          │
├─────────────┬──────────────┬─────────────────────────┤
│  3+3 模式    │  3+1+2 模式   │  传统文理分科            │
│  (6 个省)    │  (22 个省)    │  (3 个省)               │
├─────────────┼──────────────┼─────────────────────────┤
│ 浙江 上海    │ 河北 辽宁     │ 四川 河南               │
│ 北京 天津    │ 江苏 福建     │ 山西                    │
│ 山东 海南    │ 湖北 湖南     │ (等)                    │
│             │ 广东 重庆 ...  │                         │
├─────────────┼──────────────┼─────────────────────────┤
│ 语数外+6选3  │ 语数外+物理/  │ 语数外+文综/理综         │
│ C(6,3)=20种 │ 历史+4选2     │ 文/理 2 种              │
│             │ 12 种         │                         │
└─────────────┴──────────────┴─────────────────────────┘
```

**系统是怎么处理的？**

首先，每个省份都有自己的 curriculum 映射：

```python
_curriculums = {
    "北京": ["3+3综合"], "天津": ["3+3综合"],
    "上海": ["3+3综合"], "浙江": ["3+3综合"],
    "山东": ["3+3综合"], "海南": ["3+3综合"],
    "四川": ["理科", "文科"],
    "河南": ["理科", "文科"],
    "山西": ["理科", "文科"],
    # 其他省份默认 3+1+2（物理类/历史类）
}
```

其次，选科组合的识别要处理大量变体。比如用户说"物化地"，系统要识别为"物理-化学-地理"；说"史政生"，要识别为"历史-政治-生物"。

最棘手的是**分数到排名的映射**。同样的 580 分，在山东省和在北京市意味着完全不同的排名。系统通过一张"一分一段"表来解决这个问题：

```python
# 优先查一分一段表（置信度 90）
rank = query_yi_fen_yi_duan(province="山东", score=580, year=2025)
if rank:
    return rank  # 例如：山东 580 分 → 约 35000 名

# 查不到时，从录取数据反推（置信度 40）
rank = reverse_engineer_rank_from_admission(province="山东", score=580)
```

在系统提示词里，还会根据用户省份自动注入 3+3 适配提示：

```python
# 如果用户省份是 3+3 模式，注入额外上下文
if province in PROVINCES_33:
    system_msg += """
    【3+3 省份特别提醒】
    该省实行 3+3 模式，考生从物理/化学/生物/政治/历史/地理 6 科中任选 3 科。
    选科组合直接影响专业可报范围，务必确认用户的选科组合是否满足目标专业的选科要求。
    """
```
