## Phase 0: 项目画像分析

* **项目类型**：Web 应用 / API 服务（正处于从 Streamlit 到 FastAPI + 独立前端的重构期）
* **技术栈**：Python 3.11, FastAPI, Streamlit, SQLite, OpenAI API (LLM)

### 💥 角色：故障猎手 (F)
- 关注维度：部署弹性、并发冲突、数据库锁

| 编号 | 严重程度 | 问题 | 位置（文件） | 修复建议 |

| F-1 | 🟠 高危 | **多容器写入单一 SQLite 数据库易引发 Database Is Locked**。在 `docker-compose.yml` 中，`api` 服务和 `streamlit` 服务同时挂载了 `./data` 目录，极有可能并发写入同一个 `gaokao.db`。SQLite 在高并发跨进程写入时性能极差且极易报锁表错误。 | `docker-compose.yml`, `db/database.py` | 既然项目已经走向前后端分离（API + Frontend），应该废弃或剥离直接连接 DB 的 Streamlit 容器，或者改用 PostgreSQL 作为容器化部署的默认数据库。 |

### 🔴 角色：攻击者 (A)
- 关注维度：容器安全、提权风险

| 编号 | 严重程度 | 问题 | 位置（文件） | 修复建议 |
|------|---------|------|---------------|---------|
| A-1 | 🟡 中危 | **Docker 容器以 root 用户运行**。`Dockerfile` 中未指定 `USER`，进程将默认以最高权限运行，一旦发生远程代码执行 (RCE) 漏洞，攻击者可直接获取容器 root 权限。 | `Dockerfile` | 在 `Dockerfile` 尾部添加非特权用户（如 `RUN useradd -m appuser && chown -R appuser /app`，并在末尾 `USER appuser`）。 |

## Phase 4: 汇总与后续行动建议

目前项目最大的不足在于**“架构迁移的夹生饭状态”**。系统正试图从初期的“Streamlit 单体应用”向“FastAPI + 独立前端”演进，但这带来了一系列衍生问题：文档脱节、新旧入口冲突、以及容器编排配置的错乱。

**接下来的建议行动路线（按优先级排序）：**

1. **[消除精神分裂]** 决定最终架构：如果确定抛弃 Streamlit，请果断删除 `app.py` 和 `api_server.py`，并将 `README.md` 的所有指令指向 `server/main.py` 和新的 frontend。
2. **[修复锁定依赖]** 执行一次依赖锁定，导出带有准确哈希值的 `requirements.txt` 以确保生产环境不崩溃。
3. **[修复并发问题]** 在决定好唯一入口后，解决多进程访问 SQLite 导致的数据库锁问题。
