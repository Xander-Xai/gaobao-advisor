# 灾难降级 SOP 模板

> 适用于：所有面向用户的 AI 应用。确保在各种故障场景下仍能提供有价值的服务，而非直接报错。

---

## 设计原则

- **优雅降级，永不崩溃**：任何组件故障都有兜底方案
- **用户无感知切换**：降级过程中用户不应看到报错信息
- **自动恢复**：故障恢复后自动切回正常模式
- **人工兜底**：所有自动化方案都失败时，提供人工服务入口

---

## 降级分层架构

```
┌─────────────────────────────────────────────┐
│  Level 0 — 正常模式                           │
│  主模型 + 完整知识库 + 全功能                    │
├─────────────────────────────────────────────┤
│  Level 1 — 轻度降级                           │
│  备用模型 / 缩短上下文 / 启用缓存               │
├─────────────────────────────────────────────┤
│  Level 2 — 中度降级                           │
│  规则引擎 + 缓存回答 + 精简功能                  │
├─────────────────────────────────────────────┤
│  Level 3 — 应急模式                           │
│  静态页面 + 官方链接 + 人工入口                  │
└─────────────────────────────────────────────┘
```

## 场景一：LLM API 故障

```yaml
scenario: '主模型 API 超时或不可用'
detection:
  trigger: '连续 3 次调用超时（>15秒）或返回 429/500/503'
  confirm_window: '30秒内 3 次失败'

response:
  level_1:
    action: '自动切换备用模型'
    model_chain:
      - '主模型（如 DeepSeek-V3）'
      - '备用模型 1（如 Qwen2.5-72B）'
      - '备用模型 2（如 GLM-4）'
    prompt_adaptation: '切换模型时保持相同的 system prompt（你已有的 v2.2）'
    user_impact: '无感知（可能响应速度略有变化）'

  level_2:
    trigger: '所有 LLM 模型均不可用'
    action: '切换为规则引擎 + 缓存回答'
    implementation:
      - '预编译 100 个最常见的高考咨询场景及其回答'
      - '匹配方式：用户输入 → 关键词提取 → 相似度匹配 → 返回缓存回答'
      - '缓存回答头部标注："当前为快速回复模式，回答基于常见问题模板"'
    user_impact: '功能降级，但仍有基础服务'

  level_3:
    trigger: '规则引擎也不可用（如数据库也故障）'
    action: '返回静态应急页面'
    content: |
      系统正在维护中，预计 {时间} 恢复。

      在此期间，你可以：
      1. 📱 访问教育部阳光高考平台: gaokao.chsi.com.cn
      2. 📞 拨打省考试院咨询热线: {省份对应号码}
      3. 💬 加入我们的用户群获取最新恢复通知: {群号/链接}

      抱歉给你带来不便，我们正在全力恢复。
    user_impact: '功能严重降级，但提供了替代路径'
```

## 场景二：API 成本超预算

```yaml
scenario: '日/月 API 成本接近或超过预算'
detection:
  alerts:
    - threshold: '日消耗达到月预算的 4%'
      level: warning
    - threshold: '日消耗达到月预算的 5%'
      level: critical
    - threshold: '月消耗达到预算的 80%'
      level: emergency

response:
  warning:
    actions:
      - '启用语义缓存（相似问题复用历史回答，缓存命中率目标提升到 25%）'
      - '缩短对话上下文窗口（保留最近 3 轮，其余摘要化）'
      - '优化 system prompt（移除低优先级指令，缩短 token 数）'

  critical:
    actions:
      - '切换为更便宜的模型（如从 72B 降到 7B）'
      - '限制 max_output_tokens 为 500（默认可能是 2000）'
      - '对重复查询强制走缓存'
      - '通知管理层，讨论是否需要调整预算'

  emergency:
    actions:
      - '限制每用户每日最多 5 次对话'
      - '暂停非核心功能（如多轮深度分析，只保留基础问答）'
      - '使用离线规则引擎替代 LLM'
```

## 场景三：安全事件

```yaml
scenario: '检测到大规模攻击或信息泄露'
detection:
  triggers:
    - '注入拦截率突增 > 10x（如从 0.5% 飙升到 5%）'
    - '同一 IP 高频请求 > 100 次/分钟'
    - 'system prompt 内容被泄露到公开渠道'
    - '用户报告看到了其他用户的对话内容'

response:
  active_attack:
    actions:
      - '立即启用严格模式：所有输出经过二次 LLM 审核（增加延迟但提高安全）'
      - '启用 IP 级限流（每 IP 每分钟最多 5 次）'
      - '对可疑 IP 启用人机验证（如验证码）'
      - '保留所有攻击日志供事后分析'
    communication: '向用户展示："系统正在升级安全防护，可能响应稍慢，请耐心等待"'

  prompt_leak:
    actions:
      - '立即更换 system prompt 中的关键指令（发布 v2.3 紧急版本）'
      - '分析泄露路径（用户输入注入？日志泄露？API 响应泄露？）'
      - '通知所有团队成员不要在公开渠道讨论 system prompt 细节'
      - '检查 Git 仓库中是否意外提交了 prompt'

  data_breach:
    actions:
      - '立即断开受影响的数据通道'
      - '通知安全团队 + 管理层'
      - '记录受影响的用户范围和数据类型'
      - '根据 PIPL 要求，在 72 小时内通知监管部门和受影响用户'
      - '启动事件调查'
```

## 场景四：知识库故障

```yaml
scenario: '数据库不可用或数据异常'
detection:
  triggers:
    - '数据库连接超时'
    - '查询结果为空但查询条件合理'
    - '返回的数据明显异常（如分数线为负数）'

response:
  database_down:
    level_1:
      action: '切换到只读副本或缓存数据库'
    level_2:
      action: '使用预导出的 JSON 快照（每日备份）'
    level_3:
      action: '切换为纯模型回答 + 强制免责声明'
      prompt_addition: |
        【注意：当前数据库不可用，以下回答基于模型训练知识，
        可能不是最新数据。请务必到学校官网核实。】
      restriction: '禁止给出具体分数线预测，只提供通用建议'

  data_anomaly:
    action: '标记异常数据点，不使用该数据回答'
    detection_rules:
      - '分数线 < 0 或 > 750（满分）'
      - '同校同专业相邻年份变动 > 100 分'
      - '院校名称包含特殊字符或明显错误'
    fallback: '回复"该数据暂时不可用，建议到学校官网查询"'
```

## 场景五：高并发（高考出分日）

```yaml
scenario: '高考出分日流量激增（预计 10-50x）'
detection:
  trigger: '请求队列深度 > 100 或 CPU > 80%'
  peak_periods:
    - '各省出分当天 0:00-24:00'
    - '志愿填报截止前 3 天'

response:
  pre_peak_preparation:
    - '提前扩容服务器（至少 3x 正常容量）'
    - '预热语义缓存（用历史数据预先生成热门回答）'
    - '预估 API 配额，必要时提前联系 LLM 供应商扩容'
    - '准备静态页面降级方案'

  during_peak:
    level_1:
      action: '启用请求排队机制'
      user_message: '当前咨询量较大，你排在第 {N} 位，预计等待 {分钟} 分钟'
    level_2:
      action: '对简单查询优先使用缓存/规则引擎'
      routing: '关键词匹配 → 简单查询走缓存；复杂查询走 LLM（排队）'
    level_3:
      action: '限制每用户最多 3 轮对话（正常不限）'
      user_message: '当前为高峰模式，每位同学最多 3 轮深度问答，以确保更多人能得到帮助。'
    level_4:
      action: '展示静态推荐工具（根据分数+省份查院校，不走 LLM）'
```

## 降级状态监控面板

```yaml
dashboard:
  # 当前状态
  current_status:
    - component: '主 LLM 模型'
      status: '正常 / 降级 / 不可用'
    - component: '备用 LLM 模型'
      status: '正常 / 降级 / 不可用'
    - component: '知识库'
      status: '正常 / 降级 / 不可用'
    - component: '缓存'
      status: '正常 / 降级 / 不可用'
    - component: '整体服务'
      status: '正常 / Level 1 / Level 2 / Level 3'

  # 降级历史
  degradation_history:
    fields: ['时间', '触发原因', '降级级别', '持续时间', '恢复方式']
    retention: '90 天'

  # SLA 统计
  sla_tracking:
    - metric: '月度可用性'
      target: '> 99.5%'
      measurement: '非 Level 3 状态的时间占比'
    - metric: '平均故障恢复时间（MTTR）'
      target: '< 15 分钟'
      measurement: '从检测到故障到恢复 Level 0 的平均时间'
```

## 与现有项目的集成建议

1. **v2.2 system prompt** 中需要添加降级模式的 prompt 指令（如"当前为缓存模式，回答可能不是最新"）
2. **现有数据库**（3003 所院校）需要导出 JSON 快照作为降级数据源
3. **现有安全审计**（15 个漏洞）中的 API Key 泄露需要作为安全事件的首要修复项
4. **高考出分日**是你的业务峰值，需要提前做容量规划
