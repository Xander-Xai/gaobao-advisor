# 知识模块质量审计框架

> 本框架借鉴 AI-character-skill 的 6 维度结构化研究方法论，用于审计 gaobao-advisor 知识模块的质量。
> 每个知识模块在首次创建和每年更新时，应按此框架做一次审计。

---

## 一、审计维度

### 1. 来源追踪（Source Tracking）

每条关键信息必须标注来源信息：

| 字段 | 含义 | 示例 |
|------|------|------|
| source | 信息来源 | "教育部2025年就业质量报告" |
| type | 来源类型 | official_report / news / expert_opinion / data |
| date | 信息日期 | "2025-06" |
| confidence | 置信度 | high / medium / low |

**规则**：
- high = 官方报告/统计数据，有明确发布日期
- medium = 权威媒体报道/专家公开发言，有可追溯来源
- low = 行业传言/非正式渠道/过时数据（>2年）

### 2. 矛盾检测（Contradiction Detection）

检查知识模块内部和模块之间的矛盾：

| 矛盾类型 | 说明 | 处理方式 |
|---------|------|---------|
| 内部矛盾 | 同一模块内两条信息互相矛盾 | 标注矛盾，保留两种观点并标注适用条件 |
| 模块间矛盾 | 不同模块对同一专业的判断不一致 | 以更新的数据为准，标注"已更新" |
| 时效矛盾 | 旧数据与新趋势冲突 | 标注"该判断基于旧数据，建议核实" |

**示例**：
- G2 说"金融推荐（偏量化技术）" vs 00_ai_era_correction 说"金融基础岗风险极高"
- → **解决方案**：区分"金融工程/量化"（技术方向，仍有机会）和"纯金融/金融学"（基础岗被AI冲击）

### 3. 推断标注（Inference Marking）

对非直接事实的推断进行标注：

| 标记 | 含义 |
|------|------|
| `[推断]` | 基于数据和逻辑的推理，非直接引用 |
| `[观点]` | 主观判断，可能存在争议 |
| `[数据]` | 直接引用统计数据或官方信息 |
| `[案例]` | 具体个案，不代表普遍情况 |

### 4. 差距发现（Gap Detection）

识别知识模块中的信息空白：

| 差距类型 | 说明 |
|---------|------|
| 数据缺失 | 某专业/领域缺少就业数据支撑 |
| 地域覆盖不足 | 某省份或城市的录取数据缺失 |
| 时效过期 | 某条信息超过2年未更新 |
| 视角缺失 | 缺少某类用户群体（如艺术生/体育生）的建议 |

### 5. 覆盖率检查（Coverage Check）

检查知识模块对关键维度的覆盖：

| 维度 | 检查项 |
|------|--------|
| 专业覆盖 | 12大学科门类是否都有覆盖？ |
| 分数段覆盖 | 高/中/低分段都有推荐？ |
| 家庭背景覆盖 | 有资源/无资源/富裕家庭都有针对性建议？ |
| 地域覆盖 | 30省是否有基本数据？ |
| 时间覆盖 | 当前数据是否在2年内？ |

### 6. 一致性检查（Consistency Check）

检查表达风格和术语是否一致：

| 检查项 | 规则 |
|--------|------|
| 专业名称 | 使用官方名称（如"电气工程及其自动化"而非"电气"） |
| 学校名称 | 使用全称（如"华北电力大学"而非"华电"） |
| 语气 | 符合 system_prompt.md 定义的顾问人设 |
| 免责声明 | 涉及具体分数/录取线时必须加"仅供参考" |

## 二、审计流程

```
Step 1: 选择要审计的知识模块
Step 2: 按6个维度逐项检查
Step 3: 记录发现的问题（矛盾/差距/过期/不一致）
Step 4: 按严重程度分级（🔴高/🟡中/🟢低）
Step 5: 制定修复计划
Step 6: 执行修复
Step 7: 更新模块的 audit_date 字段
```
